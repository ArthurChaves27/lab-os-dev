# ATIVIDADE 5 — O shell como JCL moderno

# O slide da genealogia mostrou que o JCL usava comandos como
# // ASSIGN SYS004,TAPE para associar um trabalho a um dispositivo.
# No shell moderno, qual mecanismo cumpre papel equivalente?
# Dê um exemplo concreto do que você usou nesta atividade.

Resposta: O mecanismo equivalente é o redirecionamento de E/S do shell (<, >, 2>, |). Assim como o // ASSIGN SYS004,TAPE vinculava um número lógico de sistema a um dispositivo físico sem alterar o código do job, o shell vincula descritores de arquivo (stdin, stdout, stderr) a arquivos ou dispositivos em tempo de execução — sem alterar o programa.

Na Atividade 5, o arquivo relatorio.sh utilizou esse mecanismo para redirecionar a saída dos comandos para o arquivo de relatório:

./ola > relatorio.txt 2>&1

Aqui, stdout foi "atribuído" ao arquivo de saída e stderr foi fundido com ele — exatamente o papel do ASSIGN mapeando o número lógico SYS004 para uma fita ou impressora. O programa ola (compilado de ola.c) não sabe onde sua saída vai parar: quem decide é o shell, no momento da execução.

# ATIVIDADE 6 — Make

# 1. O monitor histórico verificava a conclusão de cada job antes
#    de despachar o próximo. No make, qual mecanismo cumpre esse
#    papel? Como o make sabe que não precisa recompilar um arquivo
#    que não mudou?

Resposta 1: O mecanismo equivalente é o grafo de dependências com verificação de timestamps. Assim como o monitor só despachava o próximo job após confirmar o término bem-sucedido do anterior, o make só executa uma receita (comando de compilação) se algum pré-requisito for mais recente do que o alvo.

O make compara o tempo de modificação (mtime) do arquivo-alvo com o de seus pré-requisitos. No Makefile da atividade, a regra ola: ola.c significa: só recompile ola se ola.c for mais novo. Se o arquivo-alvo já existe e é mais recente que todas as suas dependências, o make considera aquele passo "já concluído" e o pula — exatamente como o monitor pulava jobs finalizados. Além disso, o make respeita a ordem das dependências: um alvo nunca é construído antes de seus pré-requisitos estarem prontos.


# 2. O monitor unificava "supervisor, carregador e rotinas de I/O
#    sob uma interface textual". O que o Makefile unifica no fluxo
#    de desenvolvimento moderno?

Resposta 2: O Makefile unifica, sob uma única interface declarativa textual, todas as etapas heterogêneas do fluxo de desenvolvimento: compilação (invoca gcc para gerar ola e soma), linkagem (resolve bibliotecas e gera o executável final), limpeza (regra clean remove os binários gerados) e, opcionalmente, testes e instalação.

Assim como o monitor histórico dispensava o operador de carregar manualmente cada componente do sistema (supervisor → carregador → rotinas de I/O), o Makefile do repositório dispensa o desenvolvedor de lembrar a ordem e os flags de cada passo. Quem chegar no projeto e digitar make reproduz todo o processo corretamente — o Makefile é a "memória institucional" do build, assim como o JCL era o script de operação do job.
